# FormaAI Python 后端开发规范

版本：0.12。最近更新：2026-11-21。初版及外部来源核查日期：2026-11-19。

状态：项目规范草案，可用于后续数据库和接口设计；不代表后端代码、依赖或 CI 已实现。开发方式：SOLO-OPC，项目所有者单人配合 AI 开发，无团队协作流程。主要读者为执行开发任务的 AI；项目所有者决定产品行为与重要取舍，AI 维护实现、验证和必要说明。

## 0. AI 执行入口：单人开发与复杂度约束

本节优先约束后文的执行方式。后文的角色、评审、门禁均表示职责或自动检查，不要求设立多人岗位、评审会议、签字或逐项人工批准。

1. 每轮只完成一个可运行、可验证的业务切片：读取相关 PRD → 明确本轮必要决定 → 修改代码与迁移 → 运行相关检查 → 简短汇报结果。不得把全量设计文档完成作为开始开发的条件。
2. 直接复用现有 PRD 与本规范。产品规则写回 PRD，工程约束写回本规范；不默认新增领域设计文档、ADR 文件、评审报告或阶段总结。确有不能由代码表达的重要取舍时，在已有文档增加几行理由即可。
3. 实现后的事实优先由可执行产物表达：表结构以迁移为准，接口以实际 Pydantic 模型及生成的 OpenAPI 为准，版本以项目配置与锁文件为准，验收以测试为准。文档只保留业务意图、约束和关键取舍，不重复维护字段与接口全文；实现偏离 PRD 时仍须修正或明确产品变更，不能用代码覆盖产品意图。
4. 三个核心业务模块先作为 Python 包边界：用户、素材资产、视频制作。分类归入素材资产模块；用量统计是辅助功能，首版归视频制作模块管理；外部服务接入放基础设施 Client，不单独建立业务模块。目录按需创建，不预建空层、全部表或通用工作流引擎；不为假想的团队、多租户组织、插件、多供应商切换或微服务预留框架。
5. 默认选用满足当前需求的最简单方案。新增抽象、依赖、队列、缓存或后台机制必须对应当前用例，并说明现有做法为什么不足；不能以“企业级”“以后扩展”作为唯一理由。
6. 持久任务、用户隔离、凭证保护、状态确认及避免重复付费属于当前 PRD 需求，不能为精简而删除。采用最小可验证实现；不要求每次提交都实现完整平台级治理能力。
7. AI 自主处理已授权范围内可逆的实现细节。只有产品行为存在实质歧义、不可逆数据变更、真实费用或权限要求时才请求用户决定；不逐个询问文件名、包名和普通工具配置。
8. 只阅读与本轮相关的章节，只执行与变更及其直接依赖相关的验证；共享底层变更和发布执行相应回归。修复失败后再扩大检查，不为低风险文档或样式变更建立冗余测试。
9. 交付说明保持简短：完成了什么、验证结果、剩余阻塞。禁止将未运行检查写成通过，也不为证明工作量生成重复文档。

近期推进方式：直接讨论并实现首条链路所需的规则和表。建议先完成邮箱注册/验证/登录与用户私有分类，再进入任务创建和持久执行；远端能力只在会影响当前设计时做小范围验证，不先建设完整服务平台。

## 1. 适用范围与依据

本规范适用于 FormaAI 的 Python/FastAPI 后端、持久化任务执行器及相关迁移和测试。以 [PRD](PRD.md)、[全局业务流程](global-workflow.md)为业务依据，继承 [Java 开发规范手册](../java-development-handbook.md)中与语言无关的数据所有权、事务、幂等和可验证性原则。

规范中的“必须”是本草案建议采用的准入要求，“应”是默认做法，“可以”是有明确理由时的选择。采用后，例外必须记录适用范围、原因、风险及验证方式。PRD 未定事项不能通过代码默认值被悄悄确定；冲突时先修订并明确业务决定。

来源分为三类：PRD 产品约束、官方或维护者文档中的技术事实、FormaAI 自行选择的工程规则。PEP 8 不规定业务架构；本文的三模块划分、表所有权和发布门禁属于项目约定。[S1][S2]

2026-11-21 已新增 backend 最小工程、依赖锁文件、用户/分类 ORM 与首批迁移、基础测试和显式启用的 MySQL 集成测试。实现范围见 §3.8；其余模块仍为设计，不能把规范中描述的目标当作已经完成的功能。

## 3. 业务模块与目录

### 3.1 业务模块及数据所有权

首版建议采用模块化单体；Web 与 worker 可以分进程部署，但共用业务代码和契约，不因此拆成微服务。

| 模块 | 唯一责任 | 拥有的数据 | 不负责 |
|---|---|---|---|
| identity | 身份认证、账号生命周期及用户配置 | MySQL 一张用户表保存账号长期数据；JWT + Redis 双 Token；Redis 保存邮箱验证临时数据与限流状态，邮件通过服务商 API 发送；用户服务凭证由配置能力负责，具体加密存放方案待定 | 任务阶段、资产内容；不建立 MySQL 会话或邮箱验证表，不因凭证配置自动增加用户业务表 |
| library | 用户私有分类、长期可复用资料与参考资产 | 分类及所属内容类型、已采用调研、来源、内容提炼、视频分析、参考资产及独立文件引用 | 任务候选、完整脚本及生成视频的长期内容表 |
| production | 制作推进、执行恢复及关联用量统计 | 任务、阶段、决定、执行尝试、镜头采用与复核状态、临时产物引用、远端调用恢复记录、usage_record 用量明细 | 服务凭证持久化、供应商协议解析、钱包或预算管理 |

上表表达逻辑数据归属。已确定的表设计见本章后续约定，其余模块仍需逐项讨论；一个逻辑对象不必对应一张表。数据库设计时每张表必须登记所属模块、用户归属、写入入口和删除/保留策略。

电商、品牌、知识、故事先作为内容类型及模块内策略处理。制作模块内按任务控制、调研文字、关键帧镜头、音频合成、产物清理划分职责，不要求每个制作阶段成为独立服务。

### 3.2 建议目录

```text
backend/
  pyproject.toml
  uv.lock
  src/formaai/
    app.py                       # 应用工厂、路由与 lifespan 装配
    workflows/                   # 有明确用例的跨模块协调
    core/                        # 配置、通用错误、身份值对象、日志上下文
    infrastructure/              # 数据库、对象存储、邮件与外部服务 Client
    modules/
      identity/
      library/
      production/
    workers/                     # worker 启动与领取循环，调用业务用例
  migrations/                    # Alembic 环境及版本脚本（采用后）
  tests/
    unit/
    integration/
    acceptance/
```

每个业务包按需要增加 router.py、schemas.py、service.py、models.py、repository.py 和 contracts.py。文件承载真实职责后再创建，不批量建立空类、空接口、通用 CRUD 基类或 Service/ServiceImpl 对。

FastAPI 的 APIRouter 支持路由组合；按业务域组织包是本文结合项目规模做的选择。社区 fastapi-best-practices 提供了按领域组织的实践，本文采纳组织思路，不照搬其所有规则。[S2][S17]

### 3.3 依赖与跨模块协作

1. infrastructure 和 core 不得反向导入业务模块；app、workflows、workers 可以装配业务入口。
2. 模块不得直接导入其他模块的 ORM model、Repository 或访问其表，包括只读 SQL。跨模块通过小型查询/命令接口或已定义事件协作。
3. 跨模块契约使用明确的 Pydantic 模型、dataclass、枚举或值对象；不传 ORM 实体、Session、HTTP Request 或供应商 SDK 对象。
4. production 通过 library 的契约校验分类、读取用户主动选择的资料与资产，通过 identity 的用户配置接口获取授权使用的凭证，并调用基础设施中的外部服务 Client。Client 只处理协议与响应转换，production 负责恢复记录和用量持久化。身份由可信认证上下文传入，业务层仍执行资源归属和动作权限校验。
5. 注销、停用完成等跨模块用例由明确的协调入口组织，避免 identity 与 production 相互导入内部实现。
6. 同步返回的校验走同步业务调用；已发生且可独立处理的事实才用事件。必须恢复的后续动作采用持久化待办/outbox 或等价机制，不能依赖一次进程内回调。
7. 管理汇总查询明确查询所有者、权限、字段白名单与批量接口。不得为遵守边界制造 N+1 查询，也不得以报表为由绕开私人内容隔离。

验收：代码评审检查 imports 与 SQL，后续加入自动化导入边界检查；新增表的迁移说明必须列明所有者。

### 3.4 素材资产模块表设计

2026-11-19 根据用户要求记录本轮方案：library 管理 category、material、asset 三张表，不再拆分分类业务模块。此处记录字段语义和边界；2026-11-21 category 已实现并验证迁移，material、asset 仍待实现。生成迁移后以迁移表达结构事实，本节保留业务理由与约束。

| 表 | 职责 | 字段 |
|---|---|---|
| category | 四种内容类型下的用户私有分类 | id、user_id、content_type、name、sort_order、created_at、updated_at |
| material | 已确认采用的文字资料及分析结果 | id、user_id、category_id、title、material_type、content、sources、created_at、updated_at |
| asset | 可复用文件记录与稳定存储位置 | id、user_id、category_id、name、file_key、mime_type、file_size、created_at、updated_at |

字段与约束：

- category.content_type 表示电商、品牌、知识、故事；material.material_type 表示调研、内容提炼、视频分析。两者不混用，不按四种内容类型复制四套表。
- category 采用单层结构，名称在同一用户、同一内容类型内唯一，对 (user_id, content_type, name) 建立唯一约束。sort_order 表示展示顺序，列表以 id 作为稳定第二排序键。
- material.content 保存正文；sources 使用有明确结构的 JSON 来源列表，记录来源标题、URL、获取时间、采用摘录，用户文件来源可引用 asset_id。没有独立来源管理需求，不单独建来源表；sources 不能成为任意扩展字段。
- asset.file_key 表示稳定文件标识，不保存临时签名 URL；mime_type 表示文件类型，file_size 单位为字节。文件本体保存在持久文件存储中，宽高、时长等字段在出现明确用途后再添加。
- 三表均属用户私有。资料与素材各自属于一个分类；所有读写限定用户，关联 category_id 或来源 asset_id 时检查用户归属。
- 任务、资料和素材在各自记录中引用 category_id；分类表不保存子项 ID 列表或计数。
- 不增加标签表、版本表、来源表、素材关联表或独立文件模块。后续新增表必须有具体用例依据。

写入与保留边界：category 由分类管理用例写入，material 与 asset 由素材资产模块的确认入库用例写入；制作模块通过接口调用，不直接修改这三张表。已确认采用的调研、提炼和视频分析进入 material，可复用参考文件进入 asset。候选资料、脚本、生成镜头、音频、字幕和成片仍保存在任务私有临时空间及必要的任务控制记录中，生成成功不自动等于进入素材库。

长期素材文件独立于任务临时文件保存，任务清理不能损坏已入库内容。每项资产只属于一个分类，跨分类使用时按 PRD 另存一份。

尚未确认：分类是否可改所属内容类型、分类删除时如何处理引用，以及资料/素材删除对已引用任务的处理。此前“仅删除无引用分类”的方案仍是建议，不视为已确定规则；实现删除功能前明确，不默认级联删除。

### 3.5 视频制作模块表设计

2026-11-19 根据用户要求记录 video_task、video_shot、video_attempt、video_decision 四表方案。以下为业务字段与关系，不是已完成的物理 DDL；调度、租约及清理控制字段待执行方案确定后补齐。

| 表 | 职责 | 字段 |
|---|---|---|
| video_task | 一次独立制作的阶段与运行状态 | id、user_id、category_id、name、stage、status、input_key、checkpoint_key、version、created_at、updated_at、finished_at |
| video_shot | 镜头顺序、采用结果及复核控制 | id、task_id、shot_no、selected_attempt_id、needs_review、version、created_at、updated_at |
| video_attempt | 一次实际执行的输入、状态及结果引用 | id、task_id、shot_id、operation、status、input_key、result_key、error_code、created_at、started_at、finished_at |
| video_decision | 用户对具体版本的确认及操作决定 | id、task_id、actor_user_id、action、target_key、details、idempotency_key、created_at |

字段与关系：

- video_task.stage 表示调研、文字方案、关键帧、镜头视频、合成等业务阶段；status 独立区分待开始、运行中、等待确认、已暂停、等待重试、成功、最终失败。具体存储枚举在实现时统一。
- video_task.input_key 引用开始时固定的初始输入快照；checkpoint_key 引用当前制作进度快照，包括脚本版本、锁定规格、参考方案等。快照按版本保存，文件完整写入后才切换数据库引用，不原地覆盖导致恢复读取半成品。
- video_shot 对 (task_id, shot_no) 建立唯一约束。selected_attempt_id 可空，非空时必须指向本任务、本镜头可采用的生成尝试；只记录控制信息，不保存完整分镜脚本正文。
- 镜头脚本、参考图与衔接关系保存在制作快照中。前镜改选结果时，据衔接关系标记受影响后镜 needs_review，保留后镜旧结果；不自动重做。
- video_attempt.shot_id 对任务级执行可空，存在时必须属于同一 task_id。operation 区分调研、脚本、关键帧、镜头视频、合成等动作；input_key 固定该次实际使用的输入版本。
- video_attempt.result_key 可空，引用明确结构的结果清单，可包含多个文件及完整性信息；不为每个候选或产物机械新增表。error_code 是可分类错误，不保存私人正文或原始供应商响应。
- 用户要求重做时新增 video_attempt，保留历史。安全的查询/下载重试继续原尝试，不因网络失败另行付费生成。远端状态不明时先核对。
- 供应商请求标识、提交/核对状态及调用恢复归 production 管理；用量与费用写入本模块的 usage_record 辅助明细，通过执行尝试和实际调用关联。一次制作尝试可能需要多次不同外部操作，不假设一一对应，也不把单个 remote_request_id 硬塞成一次尝试的唯一远端请求。
- video_decision.action 包括确认脚本、确认关键帧、接受复核、跳过调研及触发合成等；target_key 绑定确切版本，details 按动作定义结构并保存必要选择，例如所选尝试 ID。不得用对旧版本的确认推进新版本。
- video_decision.idempotency_key 防止重复业务操作；具体唯一范围在 DDL 中明确，同键不同输入拒绝。记录决定与更新数据库中的任务、镜头状态在同一事务完成。
- 所有下属记录通过 task_id 确定用户归属，访问时验证任务所有者；actor_user_id 记录实际操作者，不是绕过归属验证的依据。

四表由 production 的任务、执行和确认用例负责写入。完整脚本、候选、关键帧、音频、字幕、镜头视频及成片仍位于任务私有持久存储。任务结束前禁止清理；结束后清理遵守 PRD 的两种操作，长期素材资产不受影响。

实现前按当前功能补齐：领取与租约、执行去重、清理进度、决定幂等范围与具体状态转换。注销立即阻止本地推进，远端只核对状态和费用；不能仅凭上述业务字段宣称已具备可靠恢复。表结构讨论不引入通用工作流引擎。

### 3.6 用量统计与外部服务职责调整

2026-11-19 根据用户要求记录调整：不保留独立 integration 业务模块，不推进此前 service_credential、service_request 两表提案。供应商对接归基础设施 Client，凭证归用户配置能力，远端调用恢复归 production；面向用户提供轻量用量统计。

首版 usage_record 由 production 拥有并负责写入、费用补全及查询。查询按用户隔离，管理员仅通过受限统计接口读取获准的资源用量。先采用明细查询汇总，不建立日报/月报、账单、钱包、余额或预算表。

| 字段 | 业务含义 |
|---|---|
| id | 明细 ID |
| user_id | 消耗所属用户 |
| task_id | 制作任务 |
| attempt_id | 对应执行或重做 |
| provider | 实际服务商 |
| model | 实际模型，无模型概念时可空 |
| capability | 文本、图像、视频、配音、搜索、电商数据等能力 |
| usage | 结构明确的用量与单位，例如输入/输出 Token、图片数、生成秒数 |
| cost_amount | 已知费用，未知为空 |
| cost_currency | 费用币种，未知为空 |
| created_at | 明细创建时间 |
| updated_at | 用量或费用最后补全时间 |

这些是已讨论的业务字段，不是完整 DDL。实现前必须补齐实际调用去重标识/唯一约束、统计时间口径和必要查询索引；不能仅用 attempt_id 唯一约束，因为一次尝试可能存在多个外部调用。

规则：

- 提供按日/月、任务、服务商、模型及能力的用量和已知费用统计；关联执行尝试以分析重做消耗。未知费用显式展示，不能视为免费；不同币种不直接相加，不同计量单位不混加。
- 轮询、传输重试及重复回调不得重复计数；费用后补更新同一调用的明细。实际独立计费的调用按供应商事实记录，不把每次 HTTP 请求都当成一次生成或计费。
- usage 只保存有定义的计量项，不存整份供应商响应或用户内容。费用事实与估算分开，本轮不建设估算价格系统。
- 用量明细不能替代任务恢复记录。远端请求 ID、提交结果不明、核对状态、一个尝试对应多个调用均必须可持久恢复；具体控制记录布局在实现制作执行前确定，不因撤掉模块而删除恢复能力。
- 用户配置保持按用户隔离、凭证加密与密钥分离。具体存放位置及凭证变更对未完成请求的影响仍待确定，不能因撤回独立凭证表而把密钥明文写入用户表、任务快照或日志。
- 用户注销后允许核对已提交调用状态和费用，不再下载结果。彻底删除任务时如何保留或解绑用量记录仍待产品规则确定，不默认级联删除统计或永久保留全部关联。

## 4. Python 编码与类型

1. 使用 UTF-8、4 空格缩进；包、模块、函数和变量使用 snake_case，类使用 CapWords，常量使用 UPPER_SNAKE_CASE。格式与导入排序交给 Ruff。[S1][S11]
2. 建议统一行宽 88，这是项目选择，不声称是 PEP 8 的默认要求。格式例外由 formatter 和局部规则说明处理，不混入无关批量重排。
3. 公共函数、业务用例、跨模块契约必须有参数与返回类型；使用 list[str]、X | None 等与基线版本兼容的标注。Any 仅限外部不确定数据的接入边界，校验后转为明确结构。
4. Pydantic 用于输入输出及外部数据校验；普通计算不必全部包装为 Pydantic 类。需要不可变内部值对象时可采用 frozen dataclass，但嵌套可变对象仍需处理。
5. 禁止可变默认参数；比较 None 使用 is/is not。不能用 if not value 混淆缺失、0、False 和空集合。[S1]
6. 函数名表达业务动作与单位，例如 pause_task、select_shot_result、retry_delay_seconds。find 表示允许不存在，get_required 表示不存在即失败。
7. 模块和公共业务入口使用 docstring 说明责任、前提、返回、异常及副作用。对可恢复操作说明重复调用行为；不逐行翻译代码。
8. 函数超过约 40 个非空非注释行或控制流超过三层时进行职责审查；这继承自项目手册，是评审信号，不强制拆成无意义转发函数。
9. 函数和组合优先；仅在稳定边界需要可替换实现时使用 Protocol 或抽象类。禁止用动态 getattr、反射或 dict[str, Any] 隐藏固定契约。
10. 异常转换保留原因（raise ... from exc）；禁止捕获后返回空成功。上下文管理器负责文件、连接和锁的释放；不在导入或构造阶段发请求、运行迁移或启动 worker。

## 5. FastAPI 接口与资源生命周期

### 5.1 分层职责

| 位置 | 允许职责 | 禁止职责 |
|---|---|---|
| router | 路由、绑定、调用认证依赖、调用用例、返回响应 | 业务状态分支、直接写表、供应商协议解析 |
| dependencies | 提供身份及资源生命周期、装配依赖 | 隐藏有副作用的业务流程 |
| service/用例 | 权限、状态、不变量、事务和幂等 | 操作 HTTP 报文或拼接 SQL |
| repository | 参数化持久化、明确查询条件、报告影响行数 | 决定任务推进、远程调用、私自提交上层事务 |
| client/adapter | 供应商协议、超时、响应转换 | 修改业务阶段、替用户确认或重做 |

### 5.2 输入输出契约

1. API 路径建议统一 /api/v1。写入、查询和响应使用独立模型，禁止直接序列化 ORM 全字段；凭证、密码摘要、内部调度字段不进入响应。
2. 用户身份从认证上下文获取。请求体中的 user_id、任务路径和文件名称都不是授权依据。
3. 明确缺省、显式 null 和实际值的区别。PATCH 只更新明确提供的字段；禁止把省略字段默认写成空值。
4. 写入模型建议拒绝未知字段；供应商响应按已知字段解析并制定新增字段兼容策略，不能把两种边界混用。
5. 对布尔、金额、计数和状态等敏感字段明确转换规则。Pydantic strict 模式可按字段或模型启用，但 JSON 与 Python 输入的行为有差别；日期等字段必须做端到端测试。[S6]
6. 分页有上限和稳定第二排序键；批量接口对每项资源校验归属。查询范围必须在数据库层受限，不能取出其他用户数据再过滤。
7. 业务错误代码保持稳定，HTTP 语义明确：未认证 401、拒绝访问 403、不可见或不存在 404、状态冲突 409、输入错误按统一契约使用 422。私人资源建议对越权与不存在统一返回 404，避免泄漏存在性。
8. 错误响应建议包含 code、message、request_id 与经白名单处理的 details。不能直接回传 Pydantic 原始输入、SQL、异常堆栈或供应商响应。
9. 生成/合成等长任务只返回已持久化的任务或尝试标识；202 表示已接受，不表示执行成功。状态查询和下载接口再次校验身份与归属。

### 5.3 生命周期与异步

1. 应用资源通过 lifespan 初始化和关闭，不混用同一资源的旧式 startup/shutdown 管理。[S3]
2. async def 中只直接调用不会阻塞事件循环的操作。同步 SDK 和阻塞 I/O 使用有容量限制的线程执行；媒体转码等重任务由受控子进程或 worker 承担。[S4]
3. 普通同步辅助函数被 async 路由直接调用时，不会因为其是 def 就自动进入线程池。不得把同步数据库驱动包装成 async 函数后宣称已异步化。[S4]
4. 并发有边界：连接池、每用户外部并发、全局执行并发、轮询频率与下载数量都需要配置。不设置业务预算拦截不等于无限并发。
5. 同一进程内的关联并发可使用 TaskGroup（Python 3.11+）；必须处理取消及清理，不吞掉 CancelledError。进程内 Task 不具备跨重启持久性。[S5]
6. 后台用例独立创建数据库会话，不持有已经结束的 HTTP 请求资源。异步任务携带不可变 ID/快照，不携带可变请求上下文。
7. 跨用户共享 HTTP 连接池时，每次请求显式传入该用户凭证；禁止修改全局客户端默认 Authorization、cookie 或用户上下文。

## 6. 数据库、事务与迁移

### 6.1 数据模型规则

1. 业务表使用统一的小写 snake_case；用户私有数据必须能无歧义确定所属用户。直接 user_id 或可验证父级关系均可，冗余归属字段必须有一致性检查。
   命名表达业务实体，不直接把 Python 模块名作为表名前缀。首批实现采用 user_account、password_hash、email_verified_at，具体字段以迁移为准。登录会话与邮箱验证码属于 Redis 临时认证数据，不为对应 Python 类机械建表。
2. 主键方案、MySQL 版本、字符集/排序规则、邮箱规范化、时间精度、逻辑删除字段在首批 DDL 前记录为数据库决定。不得从第三方模板继承 PostgreSQL 专属假设。
3. 日期与时间点分开；应用时间点使用有时区 datetime，接口用带时区 ISO 8601。数据库若用无时区 DATETIME，约定统一存 UTC，在驱动边界显式转换并测试。
4. 金额与精确用量使用 Decimal/定点或整数计量，并带币种和单位。费用未知保存为空或明确未知状态，不能写 0；不同币种不直接相加。
5. 唯一约束承担并发唯一性。注销邮箱仍占用注册身份，不能采用“逻辑删除后允许同邮箱新注册”的通用模板。
6. 表字段、Pydantic 契约、ORM、迁移的可空性和枚举保持一致。所有逻辑对象无需机械拆表；候选、完整分镜脚本与生成媒体不设长期业务内容表。

### 6.2 查询、会话与事务

1. 所有值参数化，动态排序或列名由服务器白名单选择。显式选择需要的数据，禁止 SELECT * 或无限加载全量关系。
2. 状态写入同时约束资源 ID、用户归属、期望旧状态或版本；检查影响行数。零行不得无条件当作成功，且错误判定不得暴露其他用户资源。
3. Service 用例拥有事务；Repository 可 flush，但不得隐式 commit。短事务内完成本地状态和必要的持久待办写入，网络请求、下载和转码在事务外执行。
4. 若采用 SQLAlchemy，每请求/执行用例持有独立 Session；AsyncSession 不在并发协程间共享，连接池/引擎与会话不能混为同一生命周期。[S7]
5. 异步 ORM 显式加载需要的关系，防止响应序列化触发隐式 I/O；查询数量与数据库分页需要集成测试。[S7]
6. 跨模块事务必须明确协调者和原子性范围。可以通过装配层为参与者配置同一工作单元，但模块公共接口不能泄漏 Session。已独立提交的动作使用持久化协调与补偿，不能宣称跨事务原子。
7. 索引根据过滤、归属、排序和唯一约束设计，记录代表性查询与执行计划。单库外键可按删除语义选择，不统一禁用或盲目级联。

### 6.3 迁移

1. 若采用 Alembic，autogenerate 仅生成候选脚本，必须审查重命名、数据迁移、约束和默认值。不能把自动生成成功等同于安全升级。[S8]
2. 已执行到共享环境的 revision 不原地修改；每份脚本记录模块、前置版本、数据影响、锁风险、验证和恢复方式。
3. 迁移由独立发布步骤执行，禁止每个 Web worker 启动时竞争升级数据库。
4. 使用隔离且版本匹配的真实 MySQL 验证空库初始化、旧库升级、约束和索引一致性。SQLite 或 Mock 不能替代 MySQL 事务及 SQL 测试。
5. 破坏性迁移先确认受影响数据与恢复来源；不能仅因存在 downgrade 函数就宣称可恢复。数据库 DDL 不受应用本地事务承诺兜底。

## 7. 持久任务与恢复

### 7.1 任务状态和确认

任务阶段、业务运行状态、单次执行状态、远端请求状态分别建模。运行、等待确认、暂停、等待重试和最终结束不得混为一个失败标志；最终结束区分成功与最终失败。具体枚举名称在数据库设计中确定。

1. 开始任务时固定初始输入；仅允许 PRD 指定的受阻补资料/跳过和按最终规格调整候选脚本。
2. 脚本与输出规格一起锁定；关键帧方案确认、实际关键帧确认及手动合成节点分别生效。确认记录绑定具体版本，旧版本确认不得推进新版本。
3. 单镜重做保留执行历史，不改变锁定脚本意图、主体、参考图及制作配置。选择前镜新结果后，下游旧结果保留并标记复核，不自动重做。
4. 其他上游变更暂停原任务，创建空任务，由用户手动选择带入内容；禁止自动复制所有历史上下文。

### 7.2 持久执行与去重

1. 生成、轮询、下载和合成必须有持久化执行记录。禁止仅靠 FastAPI BackgroundTasks 或 asyncio.create_task 承载可恢复制作流程。官方 BackgroundTasks 面向进程内后台工作；持久性要求来自本项目 PRD。[S9]
2. 接受操作时先原子记录命令、业务尝试和待执行意图，再由 worker 领取。任务派发失败必须可重试；不得出现接口返回已接受但数据库没有记录的窗口。
3. 多 worker 采用条件领取、租约、过期回收和执行版本校验或等价方案。迟到 worker 的结果不能覆盖新执行；进程内锁不能作为唯一保护。
4. 明确区分业务重做与传输重试：用户重做产生新的业务尝试；安全传输重试继续使用原尝试及幂等标识。
5. 客户端幂等键限定用户与动作，保存请求摘要；同键不同输入拒绝。供应商幂等键与本地唯一约束配合，但不承诺跨网络“恰好一次”。
6. 提交超时可能表示远端已接收；请求标记为待核对，先按供应商幂等键/请求标识查询。供应商不能核实时，等待用户决定，不能自动重新付费提交。
7. 如使用队列，消息允许重复和乱序；消费者校验版本并去重。Celery 的重投递/重试配置不自动保证业务幂等，是否引入它需要单独决定。[S10]

### 7.3 暂停、注销与恢复

| 情况 | 必须执行的行为 |
|---|---|
| 普通暂停 | 停止后续工作派发；继续跟踪和接收已提交请求结果，不进入下一阶段 |
| 服务重启/页面关闭后恢复 | 先核对持久状态、远端请求和本地产物；文件存在不等于内容完整 |
| 结果缺失且无法获取 | 停在对应阶段，等待用户确认重新生成 |
| 账号停用中 | 禁止新任务，允许处理已有任务；全部结束后完成停用 |
| 账号注销 | 立即阻止本地业务推进与新提交；已有远端请求仅核对状态与费用，不再下载结果 |
| 管理员恢复账号 | 保留未完成任务，用户逐个选择继续，不自动启动 |

派发和执行副作用前必须检查最新账号/任务控制状态，不能只在 HTTP 入口检查一次。明确已发送到远端的请求无法通过本地状态撤回；定义派发授权的并发顺序，并测试注销与派发竞争。注销后到达的远端结果不得触发下载或推进。

不能用删除任务记录来实现暂停。注销中本地在途媒体处理需要受控取消/停止，且其迟到结果不能重新激活任务；远端请求则遵守上表的核对规则。

## 8. AI、外部服务与文件

### 8.1 服务适配与凭证

1. 为文本、图像、视频、配音、搜索和电商数据定义明确输入输出，供应商原始协议只存在于适配器。先核对服务是否支持指定参考方式，不伪造支持或静默改变制作方案。
2. 用户凭证加密保存，密钥与数据库分离，记录密钥版本并设计轮换；响应只显示掩码。密码采用单向摘要，服务凭证需要可恢复加密，两者不可混用。
3. 凭证按所属用户与能力查找；用户之间不共享默认凭证、对话、cookies、缓存键或输出目录。
4. 明确连接、读取、写入和连接池超时，并另设整体操作截止时间。HTTPX 提供不同阶段的超时配置；网络读取超时不能当作整个生成任务时长上限。[S13]
5. 重试按提交/查询/下载分别定义，包含上限、退避、抖动和限流响应处理。禁止外层与 SDK 内层无协调地叠加重试；不能对全部异常自动重试付费操作。
6. 模型输出、网页正文和附件都是不可信输入。模型输出须校验结构及业务约束；其中的指令不能更改权限、凭证、下载目的地或已锁定配置。
7. 用量与费用保留供应商标识、单位、币种和来源；供应商费用与本地估算明确区分。不能仅凭状态成功推导收费为 0。
8. 更新/删除凭证对未结束任务的影响是 PRD 待定项；实现前确定引用版本、失效与恢复规则，不能静默用另一把凭证续跑。

### 8.2 网络访问与内容安全

联网调研和远端结果下载必须防范 SSRF：校验协议与解析地址，阻止回环、内网、链路本地及云元数据目标；限制重定向并逐跳验证，避免仅检查初始域名。结合出站网络策略处理 DNS 变化；为内容大小、下载时长及解析资源设置上限。[S15]

本机服务若需要访问明确配置的本地端点，应通过受控配置单独允许，不允许用户提交的任意资料 URL 获得同等网络权限。网页、模型输出不能成为 shell 参数字符串；媒体命令使用参数数组并限制输入路径。

### 8.3 临时与长期存储

1. 任务私有目录使用服务器生成标识，归属路径只是辅助隔离，实际读写仍校验授权。禁止信任上传文件名或允许路径穿越。
2. 临时产物使用持久卷或等价持久存储，不放入随容器销毁的临时目录；上传、生成和下载记录写入中、完整、缺失或失败等真实状态。
3. 文件写入完成并校验后才能登记为可用。数据库与文件系统/对象存储不共用本地事务，必须有可重试登记、删除及孤儿对象核对机制。
4. 存对象 key、校验值及必要元数据；短期签名 URL 不能代替稳定文件引用。签名 URL、私有内容和本机绝对路径不进入普通日志。
5. 已确认采用的长期资产须独立保存，再登记入库。任务清理不能损坏已入库内容，入库动作必须幂等且能恢复部分失败。
6. 仅允许清理成功或最终失败任务；暂停、运行、等待确认和等待重试均不可清理。清理操作区分仅临时文件与彻底删除任务。
7. 清理先记录可恢复意图，按受限清单删除并报告结果；部分失败不能伪装完成。清理期间通过任务状态/版本防止恢复或再次执行竞争。
8. 业务不自动清理临时产物；孤儿核对不得被实现为绕过保留规则的定时删除。彻底删除后请求/费用记录的保留范围在设计前明确，不自行无限保留。

#### 推荐决策与最小状态

| 项目 | 本项目建议及理由 |
| --- | --- |
| JWT 库与算法 | 使用 PyJWT；单体先固定 HS256。Access/Refresh 使用两把独立 CSPRNG 生成的至少 32 字节密钥；不提供默认值、不允许客户端决定算法。未来确有独立验签服务再考虑非对称算法，不预建 JWKS 服务。实际兼容版本待 uv 锁定及 Python 3.14 测试。 |
| Token 类型 | Access、Refresh 均为 JWT，签发和验签函数分开。分别固定 typ、aud、token_type，并检查 iss、sub、sid、jti、iat、exp、ver。sub 为正整数用户 ID 的字符串；其余字段严格校验类型、长度和时间关系；不允许 bool 冒充整数。 |
| JWT 内容 | 不携带邮箱、密码、服务凭证或私人内容；role/status 从 MySQL 实时读取，不信任 JWT 中的权限快照。sid、jti 分别使用独立的至少 128 bit 安全随机值。 |
| 时间 | 建议 Access 5 分钟；Refresh 空闲 7 天、整个会话绝对 30 天。刷新后 exp=min(now+7天,绝对截止)，Access 也不超过会话截止。Access 时间偏差容忍建议 30 秒；Redis 到期与 Refresh 截止不借偏差延长。数字是项目建议，不是 RFC 强制值。 |
| 浏览器保存 | Access 仅在内存，经 Authorization: Bearer 发送；Refresh 仅由 HttpOnly Cookie 保存，不在 JSON 返回。不使用 localStorage 保存任一 Token。建议生产同源部署，前端开发通过代理保持同源。 |
| Cookie | 生产名称 __Host-formaai_refresh，Secure、HttpOnly、SameSite=Strict、Path=/，不设置 Domain；Max-Age 不超过本次 Refresh 剩余寿命。开发 HTTP 必须使用独立名称与显式开发配置，生产拒绝不安全配置。删除使用相同名称、路径和域属性。 |
| CSRF | Cookie 认证的 POST 接口强制检查精确 Origin 白名单，拒绝缺失、null 或不匹配来源；要求 X-CSRF-Protection: 1 与 application/json，拒绝简单表单 Content-Type。该头用于强制非简单请求，不是秘密。严格 CORS 与 SameSite 作为配套，不能只检查 Cookie。登录也适用，防止登录 CSRF。若后续接受 HTML form，重新选择同步 CSRF Token 方案。[A3][A4] |
| 服务端认证 | 每次保护接口都检查 JWT、Redis 会话、MySQL 最新账号状态与版本。先不缓存状态/角色，以免撤销滞后。认证仅建立身份，资源 owner 校验仍在用例内，管理员不能越过私人内容隔离。 |

JWT 解码必须显式限制算法并要求必要 claims；库验证某个 claim 的值，不代表它要求该 claim 一定存在。不得把未验签 payload 用作可信身份，不读取 Token 指定的远端密钥地址。[A1][A6]

Redis 首版只增加一种认证业务 Key：`formaai:<env>:auth:session:<sid>`（Hash）。字段为 `user_id`、`account_version`、`refresh_digest`（完整 Refresh JWT 的 SHA-256）、`absolute_expires_at`、`refresh_expires_at`。Key TTL 等于 Refresh 当前截止时间，签发和轮换通过同一 Lua 操作写字段及到期时间。Redis 不存明文 JWT；不为每次刷新追加永久记录，不维护用户会话索引、不做全库 KEYS/SCAN 撤销。Refresh 自包含签名仅负责合法性验证，不能替代会话存在性与摘要匹配。

全账号撤销建议复用 `user_account.version`，JWT 的 ver 与 Redis account_version 都保存签发时版本；认证时和 MySQL 最新版本比较。撤销执行 `version=version+1` 并提交，旧会话即使 Redis 清理失败也失效，等待自然 TTL 清理即可。**明确代价：version 同时是乐观锁，所有推进该版本的账号修改都会要求重新登录。** 当前账号表都是身份/安全数据，可接受此保守策略作为建议；日后加入普通偏好设置时，不得无意识延续此副作用。若需要普通账号修改不退出，再评估同一用户表内的持久安全版本字段，而非临时会话字段。所有账号写入入口必须明确推进版本，当前 ORM 没有自动配置 version_id_col，不能假设已实现乐观锁。

#### 四条执行路径

1. **签发。** 仅由已完成凭证验证的内部用例调用；不提供按 user_id 直接发 Token 的公开接口。读取账号状态/版本，生成 sid、两个 jti 及 Token，Lua 仅在 sid 不存在时创建会话并设置 TTL；Redis 失败不返回 Token。响应 `Cache-Control: no-store`，只返回 Access、token_type、expires_in，并设置 Refresh Cookie。首次工程测试可直接调用内部服务；真实登录仍需后续密码验证与限流。
2. **刷新。** 先完成来源、JWT 类型/签名/claims、MySQL 状态/版本检查，再预生成新 Token 对。Lua 单次完成会话存在性、归属、版本、时间和旧摘要检查；匹配才更新摘要及 TTL。合法且未过期的同一 sid Refresh 摘要不匹配，删除该会话并返回重放错误；缺失会话只拒绝，绝不重建。无效签名或错误类型不得触发撤销，避免伪造请求踢用户下线。脚本写入前完成所有格式/类型检查：Redis Lua 原子执行不等于异常自动回滚。[A2][A5]
3. **当前会话退出。** POST 接口校验 Cookie 来源及有效 Refresh JWT，通过 sid/用户归属原子删除该会话；允许已轮换但签名有效的同会话 Refresh 撤销其家族，不能撤销其他 sid。会话已无效时幂等成功并清 Cookie；无凭证也可清本地 Cookie。Redis 不可用且无法确认撤销时返回 503，不把单纯删除浏览器 Cookie 宣称服务端退出成功。后续 Access 验证因会话不存在而失败。
4. **全账号撤销。** 内部 `revoke_all_sessions(user_id)` 通过 MySQL 原子递增版本完成；若做用户入口，用当前账号认证并在更新事务中复核版本/状态。修改密码、完成停用、注销及恢复与版本推进放在同一 MySQL 事务。Redis 不承担此事务的提交条件，不增加分布式事务；MySQL 提交结果不明返回失败且不声称已撤销，重复推进版本仍安全。普通当前会话退出不推进用户版本。

首版建议**严格一次刷新**，不增加旧 Token 宽限期、旧新 Token 映射或加密响应缓存。两个标签页同时刷新旧 Token，先执行者可轮换成功，后执行者触发家族撤销，先返回的新 Access 也随后失效。这是严格策略的明确代价，不是两个请求都能成功。前端使用跨标签页互斥与消息协调，获得互斥后再发请求，由浏览器自动携带当时的 Cookie；JavaScript 不能读取 HttpOnly Refresh。若平台无法协调，必须接受重新登录，不能声称仅页内 single-flight 已解决多标签页。

刷新结果丢失或 Redis 写入超时后，不自动重试原 Refresh、不由 HTTP/Redis 客户端透明重试非幂等轮换，也不把失败当成功。用户可能需要重新登录。未来有真实可用性证据才引入带请求身份、短期限且绑定同一会话的幂等重试设计；不能把所有旧 Token 使用当作合法重试。刷新成功不撤销该 sid 的旧 Access，它在原 5 分钟期限内仍有效；退出或重放会撤销该 sid 的全部 Access。

#### 账号状态、并发与故障边界

| 状态/事件 | 本项目行为 |
| --- | --- |
| active | 允许正常认证；业务权限另行判断。邮箱验证要求在注册/管理员建号接入时明确，不擅自绕过，也不在本轮伪造验证流程。 |
| disabling | 仍允许认证、刷新和处理已有任务；明确禁止创建新任务。不能在通用认证依赖中统一拒绝此状态，否则违背 PRD。 |
| disabled / deleted | 拒绝认证与刷新；相应状态写入同时推进版本。恢复 active 时再次推进版本，必须重新登录。 |
| 角色调整 | 使用最新 MySQL role；版本推进使旧凭证失效。管理员身份不自动获得用户素材/内容权限。 |
| 退出与后台任务 | 退出会话不停止持久任务。worker 不携带用户 Access Token 执行长任务；按 PRD 在派发和副作用前检查持久账号/任务状态。 |

当前会话撤销和刷新按 Redis 脚本执行顺序确定：撤销先执行则刷新不能重建；刷新先执行则后续撤销删除新状态。全账号撤销、角色/状态变更以 MySQL 提交后的版本作为新认证的判断依据；并发签发捕获旧版本的 Token 必须在后续认证失败，不能在刷新时自动升级为最新版本。每个认证查询使用短生命周期 Session，避免复用长事务旧快照。Redis 与 MySQL 之间仍有在途窗口，不能声称一次依赖校验撤回所有已放行请求；敏感业务写入须在自身事务内复核版本/状态，与账号变更按行锁或条件更新排序。新任务派发竞争留给 production 用例实现及验收。

Redis/MySQL 不可达返回 503；缺失或已过期凭证返回 401；合法身份的动作不允许返回 403；私人资源不属于用户返回 404；滥用限流返回 429。认证失败应包含适当的 Bearer challenge，不能把基础设施故障伪装成密码错误或无限触发前端刷新。日志只记 request_id、内部事件码、必要用户标识，不记录 Cookie、JWT、密钥或摘要；计数刷新成功、重放、撤销、依赖故障即可，不预建观测平台。

Redis Key 丢失/淘汰时 fail closed，要求重新登录；连接失败时不得退化为纯 JWT。首版按现有单 Redis 部署，认证读取主节点，不引入副本读与自动切换。上线必须明确认证状态的持久化与恢复策略：若该实例仅承载可丢失认证/验证码数据，可采用重启丢弃会话；若有其他数据，不得擅自关闭整实例持久化。**旧快照恢复或异步复制回退可能复活已删除会话/已消费 Refresh，TTL、Lua、AOF、WAIT 都不能独立消除此风险。** 遇到 Redis 数据恢复/角色切换，在重新开放认证前清除认证会话并轮换两把 JWT 密钥、撤掉旧验签密钥；先阻断所有实例认证流量，再同步配置，验证旧凭证全部失败后恢复。若部署不能执行此恢复门禁，不能宣称满足即时撤销保证。[A7]

#### 落地顺序与验收

实施前明确两项体验取舍：严格轮换在多标签页并发或响应丢失时可能使整个会话退出；复用账号 version 会使所有推进版本的账号修改撤销旧凭证。二者是首版减少状态和跨存储协调的项目建议，不是“业界标准必须如此”。独立安全版本仍可保留单用户表，但会增加字段及迁移；有限幂等刷新会增加响应恢复状态及攻击面。当前方案先保留上述保守建议，不将其隐式升级为已批准的产品行为。

按需增加 identity 下的 `tokens.py`（claims/编码验签）、`sessions.py`（Redis Lua及会话操作）、`service.py`（用例编排）、`dependencies.py`（身份及动作依赖），首次提供实际路由时再增加 `router.py`、`schemas.py`。复用现有配置及连接池，在 app 装配处暴露依赖，使用同步 def 依赖/路由或明确线程池隔离，不在 async def 内直接阻塞调用同步 MySQL/Redis。无新 MySQL 表、无通用 Repository/抽象认证框架。

建议接口契约：`POST /api/auth/refresh` 返回 Access JSON + 新 Refresh Cookie；`POST /api/auth/logout` 返回 204；`POST /api/auth/logout-all` 在实现时明确纳入范围后返回 204；认证依赖使用 HTTPBearer，不靠 OAuth2PasswordBearer 宣称存在尚未实现的 OAuth 登录端点。登录路由和真实 `/me` 放入后续登录切片。业务依赖分别表达 `get_current_user`、`require_admin`、新任务操作许可；避免一个 `require_active_user` 错误屏蔽 disabling 用户。

1. 添加必需签名密钥、issuer、audience、TTL、Cookie/来源配置；完成 PyJWT 锁定和纯 Token 测试。仅安装实际用到的依赖，密码库留到登录切片。
2. 用真实隔离 Redis 实现签发、原子轮换、撤销和 TTL；复用真实 MySQL 测试设施验证版本与状态，不把 fakeredis 视为 Lua/并发的全部证据。
3. 接入认证依赖与刷新/退出路由；测试 HTTP Cookie、Origin、CORS、错误响应及脱敏。接口完成后，以代码/OpenAPI取代本节重复细节。

完成标准：算法/类型混淆、缺失 claims、错误受众/发行者、过期/未来时间、错误 sub、篡改与跨用户会话均拒绝；同一 Refresh 两个并发请求验证严格重放结果；验证刷新/当前退出两种执行顺序、签发/全撤销竞争、全撤销后 Redis 旧会话仍存在也不可用、disabled/deleted 恢复后旧凭证失败；验证 disabling 可处理已有任务但不可新建的依赖策略；模拟 Redis 写成功后响应丢失、超时和断连，不透明重试；校验空闲/绝对 TTL 不被延长、撤销后 Access 失效、无状态降级；验证 Cookie 属性、CSRF、任意来源拒绝及日志不泄密。状态改变与业务任务的端到端竞争，须等 production 实现后验证，不能由认证单元测试冒充。

本轮为方案与资料核查，没有安装 PyJWT、修改业务代码/配置/迁移或运行上述验收。剩余两项：恢复 302 专业调研调用并复核；实现时落实部署来源与严格轮换的重新登录体验。默认继续上述最小方案，不额外制造团队评审文档。

### 9.2 通用安全约束

1. 密码采用成熟实现的自适应密码哈希，建议 Argon2id；参数按部署资源验证，不自行设计哈希算法。[S14]
2. 邮箱验证码或令牌必须过期、单次使用且限制尝试次数；登录、注册、验证接口有防滥用限制。错误信息不得直接暴露某邮箱是否注销或某资源是否属于他人。
   邮件通过第三方邮箱服务商 API 发送，Redis 保存验证临时数据、有效期、尝试次数及发送/校验限流状态，验证成功后安全消费；用户表只保存账号长期数据和必要验证结果。Redis 数据缺失或不可用时不得绕过验证；不能将 Redis 验证消费与 MySQL 注册提交宣称为同一原子事务，注册失败和重复请求需定义可重试行为。服务商发送失败须如实返回，不能把请求发出等同于用户已收件。
3. 认证方案确定为 JWT + Redis 双 Token：Access Token 用于访问业务接口，Refresh Token 用于换取新的访问凭证，Redis 管理会话有效性、刷新及撤销状态。用户模块只保留一张 MySQL 用户表，不新增 Token、会话、邮箱验证或限流表。注销、完成停用及退出登录按各自范围使认证失效，恢复账号不得复活旧凭证。
   具体签名算法、有效期、Token 传输/保存方式、刷新轮换与并发处理在实现时确定并测试，不在用户表加入对应临时字段。Redis 不可用时不得静默退化为仅验证 JWT 签名的放行模式。若使用 Cookie，落实 HttpOnly、Secure、SameSite 与 CSRF；CORS 不是认证或 CSRF 防护的替代。
4. 管理员只能通过字段白名单获取账号信息、状态、用量与脱敏错误，不获得私人内容、附件、提示词或凭证下载能力。
5. 配置从受控环境/秘密管理来源读取，启动时校验必需字段；仓库只放无密钥示例。禁止自动启用默认生产管理员密码或使用空配置伪造成功。
6. 日志记录 request_id、任务/执行标识、阶段、耗时和脱敏错误类型；不记录密码、Token、完整用户输入、完整供应商响应或带签名地址。
7. 用户/任务上下文通过明确参数或受控 ContextVar 传递并在 finally 恢复；不存于进程全局变量。跨用户压力测试验证日志和结果不会串线。
8. 监控领取积压、租约回收、待核对请求、恢复失败、外部限流、下载失败和磁盘余量。错误、trace 和指标标签不包含私人正文及高基数敏感内容。
9. 审计记录谁在何时执行了确认、重做、注销、恢复、清理等操作；审计保留期限与脱敏规则在部署前确定，不能默认记录全部内容。

### 10.3 部署与验收门禁

1. 应用与 worker 启动/关闭路径都要验证资源回收；进程退出前停止领取新工作，在途工作记录可恢复状态。
2. 多 Web worker 不得各自无约束启动同一调度循环；周期调度需要唯一归属或数据库领取去重。
3. 发布采用同一锁文件和构建产物；迁移前检查备份、兼容窗口、锁影响和恢复方案。健康检查区分进程存活与核心依赖可用。
4. 新增模块/表/外部动作必须提供边界、归属、授权、幂等、失败恢复与对应测试。
5. 覆盖率可以辅助识别遗漏，但不替代上表核心场景；不虚构尚未测量的性能承诺。并发和磁盘阈值根据代表性视频任务实测确定。

## 11. 评审清单与待定决定

### 11.1 每次变更检查

- 是否对应 PRD 用例，且未自动复用历史、自动重做下游或自动清理？
- 表是否有唯一所有者，跨模块访问是否经过契约？
- 请求、后台执行、查询和下载是否都校验用户归属？
- 未确认的脚本、关键帧或合成步骤是否无法推进？
- 本地事务是否短，状态更新是否检查旧版本和影响行数？
- 外部提交不明时是否先核对，而非自动重付费？
- 任务重启、暂停、注销和恢复是否符合不同规则？
- 临时与长期文件是否生命周期独立，部分失败是否可恢复？
- 未知费用是否仍为未知，管理员是否只得到允许字段？
- 迁移、真实数据库与异常路径测试是否有明确结果？
